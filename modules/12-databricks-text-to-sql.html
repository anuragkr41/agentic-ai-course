1. Unity Catalog fundamentals

Unity Catalog (UC) is Databricks\' governance layer. Three-level namespace:

  • Catalog — top-level (typically per environment: prod, staging).
  • Schema (database) — groups related tables/views (prod.sales, prod.support).
  • Table / View — the actual data.

Permissions are granted at any level. Row-level filters, column masks, and lineage tracking are first-class. Snowflake and BigQuery have equivalents (Snowflake DB.SCHEMA.TABLE + dynamic data masking; BigQuery dataset.table + policy tags). Patterns in this module transfer.

2. Views-only pattern

Rule: the agent\'s SQL credential has access to views, never base tables. Views are designed for AI access — they:

  • Filter rows (only rows this caller is allowed to see)
  • Mask columns (no SSN, no full credit card numbers)
  • Compute pre-aggregated fields (saves the agent from having to do joins it might get wrong)
  • Document themselves with column descriptions

Architecturally, this is the same idea as Module 9\'s allowlists — narrow what the agent can touch. Cannot exfiltrate what cannot be reached.

3. Schema-aware SQL generation

The cardinal rule of Text-to-SQL: inject the relevant schema into the prompt. Don\'t hope the LLM knows your table layout — give it the columns, types, and descriptions for the views in scope.

4. SQL validation (SELECT-only + LIMIT)

Before any generated SQL is dispatched, validate:

  • SELECT-only. Parse the SQL. Reject anything that isn\'t a SELECT statement. No INSERT, UPDATE, DELETE, DROP, CREATE.
  • Referenced objects on the allowlist. Parse the FROM clauses. Confirm all tables/views are on the configured allowlist (typically the v_* views in your catalog). Reject if anything else.
  • LIMIT enforced. If the query doesn\'t have a LIMIT, inject one (e.g., 1000). Stops a runaway SELECT * from scanning a 10TB table.
  • Cost preview. For Databricks SQL or BigQuery, you can dry-run the query — get the estimated bytes scanned before executing. Block queries above a threshold.

5. Approval gate

For non-trivial queries, route through HITL before execution. The reviewer sees: the user\'s question, the generated SQL, the LLM\'s explanation, the dry-run cost. Approve / edit / reject. (Same pattern as Module 1.)

Which queries to gate:

  • Anything writing to a table (in our pattern: only the run registry, but if you allow more, gate them).
  • Anything above a cost threshold (e.g., >1GB scanned).
  • Anything from a new user without a track record.
  • First time the agent sees a never-before-asked question pattern.

Auto-approve everything else, but log and sample-audit 5–10%.

6. Results in Delta + run registry

Once approved and executed:

  • Write the result set to a Delta table (Databricks\' open table format). Now reusable, auditable, and version-controlled.
  • Log a "run registry" row: user, original question, generated SQL, approver, execution time, bytes scanned, result-set Delta path. Searchable. Compliance-ready.
  • Return a link, not the data, for large result sets. User opens the Delta result in a notebook or BI tool — keeps PII contained, supports reuse.

Likely interview / investor / hiring questions

Q: How do you stop a Text-to-SQL agent from running a destructive query?
A: Four layers. (1) Credential scope — the agent\'s DB credential has SELECT-only privilege at the warehouse level. INSERT/UPDATE/DELETE/DROP are impossible regardless of what SQL is generated. (2) View-only access — agent can\'t name base tables; they\'re not in its allowlist. (3) Parser validation — every generated query is parsed; non-SELECT or non-allowlisted-views are rejected before dispatch. (4) Cost / size limits — dry-run estimates bytes scanned; queries above threshold gate to a human. Together: defense in depth. No single layer is sufficient; no single layer needs to be.
Q: A user asks "how many enterprise customers churned last quarter?" — walk through what your system does.
A: 1) Inject schema for the relevant views into the prompt: v_customers with column metadata. 2) LLM generates structured output: { sql, explanation, confidence }. 3) Parser validates: SELECT-only ✓, views-only ✓, LIMIT injected. 4) Dry-run estimates 200MB — under threshold, auto-approve. 5) Execute on Databricks SQL Serverless. 6) Write the result to a Delta table; insert a row into the run registry with user, question, sql, timings, cost. 7) Return a link to the result for the user to open in their notebook or BI tool.
