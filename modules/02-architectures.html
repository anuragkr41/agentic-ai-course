1. Why patterns matter (and which six to know)

A "pattern" is a named, reusable solution to a recurring problem. The reason patterns matter in agentic AI is the same reason they matter in software architecture: they compress communication. You say "supervisor-worker with HITL gates" and a senior engineer immediately understands ~80% of your design.

For founders, patterns do three things:

  • They make your brief specific. "Build a planner-executor with a router on top" beats "build an AI thing that does the work."
  • They flag tradeoffs early. Each pattern has known weaknesses. Knowing them up front lets you reject a pattern before burning a quarter on it.
  • They survive vendor changes. The pattern is the same whether your team uses LangGraph, Microsoft Agent Framework, AWS Bedrock AgentCore, or Vertex AI. Vendors come and go; patterns stay.

The six patterns this module covers — router, planner-executor, supervisor-worker, ReAct, reflection, tool-use, planning — are the ones you'll see referenced in every serious 2026 talk. They're not exclusive of each other; a real system layers several.

3. ReAct — the foundational reason + act loop

ReAct (Reason + Act, Yao et al., 2022) is the single most important pattern in agentic AI. Almost every modern agent has a ReAct loop somewhere inside. The intuition: the LLM alternates between thinking and acting, observing the result of each action before deciding the next step.

Concretely, a ReAct trace looks like this:

Thought: I need the customer's order date to check the policy.
Action: lookup_order(order_id="4821")
Observation: { date: "2026-05-10", amount: 200, status: "shipped" }

Thought: Order is 8 days old, within the 30-day refund window. Let me confirm the damage report.
Action: lookup_damage_report(order_id="4821")
Observation: { reported_at: "2026-05-15", photos: 3, severity: "high" }

Thought: All criteria met. I'll propose a $200 refund.
Action: propose_refund(order_id="4821", amount=200, reason="damage")
Observation: { status: "pending_approval", ticket: "#R-981" }

Thought: Done. Goal achieved.

Three things to know about ReAct in production:

  • It can loop forever. If the LLM picks bad actions, it just keeps thinking. Always set a max-iterations budget (typically 5–15). When hit, escalate to a human or return a partial result.
  • The Thought step is the audit trail. Log every thought verbatim. When an agent does something wrong, you'll need to read its reasoning to debug. This is gold for both engineering and compliance.
  • Tools must be well-specified. Bad tool descriptions = LLM picks the wrong tool. Module 8 (MCP) standardizes this; for now know that tool name + description + input schema is what the LLM sees.

4. Reflection / self-critique

Reflection adds a critic on top of a generator. The LLM produces an output, then a (usually same) LLM critiques that output against criteria, then the generator revises. Loop until the critic is satisfied or you've spent your budget.

When to use reflection:

  • Yes: high-stakes outputs (legal drafts, financial summaries, customer-facing copy), code generation, complex reasoning where errors compound.
  • No: simple classification, low-stakes drafts, real-time interactions where latency matters more than polish, anything you'll review by hand anyway.

The reflection trap

Adding a critic doubles your LLM cost and latency per iteration. If your generator is already 90% accurate, the critic might only catch one mistake per 100 — and you've paid 2× for everyone. Measure first; add reflection only where data shows it pays back.

5. Tool-use pattern (and contracts)

"Tool use" sounds trivial — the agent calls a function. It isn't. The reason this is its own named pattern: how you describe the tool determines whether the LLM picks the right one. Good tool descriptions are the difference between a working agent and an embarrassing demo.

The cardinal rule of tool contracts: the description is the prompt. The LLM picks tools based on names + descriptions. So:

  • Verb-first names. lookup_order, send_email, propose_refund. Not OrderUtility.
  • One sentence description. Says what it does AND when to use it. "Fetches order details by ID. Use before any refund decision."
  • Strict input schemas. Required vs optional fields, types, allowed values. Schema = validator = guardrail.
  • Mark side effects. "Read-only" tools are safe to call freely. "Write" tools should route through a HITL gate (Module 1).
  • Idempotency keys on write tools. Calling send_email twice should not send two emails.

6. Planning pattern

Sometimes ReAct's "decide one step at a time" isn't enough. If a task has 10 dependent steps and the first decision shapes the rest, you want the agent to plan the whole thing first, then execute. That's the planning pattern (also called Plan-and-Execute or Plan-and-Solve).

Workflow:

  1. Plan. The LLM reads the goal and outputs a numbered list of steps. No tools called yet.
  2. Execute. Each step runs (typically using ReAct internally for the actual tool calls).
  3. Reassess. After each step, check: is the plan still valid given what we observed? If not, re-plan.

When planning beats ReAct:

  • Many dependent steps. Booking travel: flight choice constrains hotel, which constrains itinerary.
  • You need to show users / auditors the plan before committing. "Here's what I'll do — approve?" — this is essentially HITL on the plan.
  • Parallelizable steps. Once you have a plan you can run independent steps in parallel.

When planning hurts:

  • Tasks are short. The plan is just one step long.
  • Reality changes fast. The plan goes stale before you finish executing it.
  • You don't have the data to plan well until you've explored — in which case ReAct is the explorer.

7. Design considerations: latency, cost, reliability, auditability

Every pattern choice you make trades these four off against each other. Founders who can't articulate this lose investor questions in 60 seconds. The framing:

LeverWhat it meansHow patterns affect it
LatencyHow long the user (or downstream system) waits.Routers: fast. Planner-executor: slower (plan + steps). Reflection: 2× per loop. Multi-agent: depends on parallelism.
Cost$ per task (mostly LLM tokens).Each LLM call costs. ReAct = N calls. Reflection = 2N. Multi-agent = N × agents. Plan-then-execute can be cheaper than pure ReAct on long tasks.
ReliabilityHow often the agent achieves the goal correctly.Reflection adds reliability at cost. Planning helps long tasks. Schema validation on tool outputs is the cheapest reliability gain.
AuditabilityCan you reconstruct what happened and why?ReAct's Thought log = audit trail. Plans = pre-commitment. Multi-agent = harder (cross-agent traces). HITL gates create natural audit checkpoints.

Practical rules of thumb:

  • Latency under 2s for user-facing chat. Use the cheapest pattern that hits this — usually router or single-agent ReAct with a max-iteration cap.
  • Latency under 30s for "agent thinking" UX. Show progress (e.g., "Looking up order…"). User tolerates more.
  • Latency above 30s → batch mode. Email or webhook when done. Use planning + parallelism.
  • Cost budget per task. Pick it explicitly. If the LLM call ceiling is $0.05, ReAct with 5 iterations on a cheap model is fine; multi-agent with reflection is not.
  • Reliability ceiling. No agent hits 100%. Pick a target (e.g., 95% task success) and engineer to that. Above 99% is heroic — and usually means you're treating users as the last line of defense (via HITL).

Founder shortcut

If you can't justify in one sentence why your design isn't a single ReAct loop, build a single ReAct loop. You can upgrade later — going from one agent to many is a refactor; going from many to one is an admission of defeat.

Likely interview / investor / hiring questions

Q: Walk me through how you'd choose between ReAct and Plan-and-Execute for a given problem.
A: ReAct decides one step at a time and observes results before the next decision — great when the right next step depends on what you just learned. Plan-and-Execute commits to a full plan first, then runs it — better when steps are dependent and you'd benefit from up-front commitment (auditable, parallelizable, human-approvable). I default to ReAct unless I need to show the plan to a user/auditor, or unless parallelism gives me real latency wins.
Q: When would you NOT use reflection?
A: When the baseline output quality is already high enough for the stakes. Reflection doubles cost and latency per loop. If my generator hits 90% on a task and the stakes are low — say internal triage notes — I won't pay 2× to catch the marginal mistake. I add reflection on high-stakes outputs: legal drafts, customer-facing emails, code, complex reasoning. Always after measuring, never speculatively.
Q: Your agent is looping forever. What pattern issue is this?
A: Almost certainly missing a max-iteration budget on a ReAct loop. The LLM keeps picking actions that don't progress toward the goal — sometimes because tool descriptions are ambiguous, sometimes because the goal itself is ill-defined. Fix: hard cap (e.g., 10 iterations), explicit "give up" tool the agent can call to escalate to a human, and verbatim Thought logs so you can debug why it got stuck.
Q: How do you make agent decisions auditable for compliance?
A: Three things. First, log every Thought, Action, and Observation in a ReAct trace — this is the audit trail. Second, force structured outputs validated against a schema before they leave the system (no "agent said something we can't parse"). Third, HITL gates on irreversible actions, with the gate decision and reviewer identity logged. Together you get a reconstructable chain: what the agent thought, what it tried, what it observed, what a human signed off, what changed in the world.
Q: Why didn't you go multi-agent for this?
A: I default to single-agent and upgrade only when (a) work decomposes by specialty, (b) parallelism materially helps, or (c) governance requires separation of concerns. For this use case none applied. Going multi-agent would have doubled cost, added cross-agent debugging, and introduced loop / deadlock failure modes — without measurable benefit. Going single-to-multi is a refactor; going multi-to-single is an admission of defeat.
