Knowledge Graphs for AI (Neo4j)

Structured memory for agentic systems. When your data has relationships that matter, graphs beat vectors.

⏱ ~70 min · 2 videos + 1 walkthrough · 10 MCQs + 3 scenarios · ≥80% to unlock M7

Why this matters

Vectors are great for "what's similar." Graphs are essential for "how things are connected." Your customers, products, suppliers, contracts, and transactions don't live as isolated chunks — they're a network. A knowledge graph (KG) makes that network queryable, traceable, and reasoning-friendly. Neo4j is the de facto standard.

You'll be able to

  • Model your domain as entities + relationships (nodes + edges)
  • Design an ontology that prevents drift and enables consistent extraction
  • Record provenance — where each fact came from and when
  • Apply constraints and schema rules to keep your KG honest
  • Traverse the graph for multi-hop reasoning (Module 7 builds on this)

1. Entity-relation modeling fundamentals

Two building blocks:

  • Nodes = entities (things). Each has a label (type) and properties. (Customer {id: 4821, name: "Anurag"})
  • Edges = relationships. Directional. Have a type and optional properties. (c:Customer)-[:PLACED {at: "2026-05-10"}]->(o:Order)

In Cypher (Neo4j's query language), the pattern reads like ASCII art: (a)-[:RELATES_TO]->(b).

2. Ontology-driven design

An ontology is your KG's schema — the allowed entity types, relationship types, and properties. Without it, LLM-driven extraction drifts: "Customer" today, "client" tomorrow, "user" the day after. Same thing, three labels, queries break.

Three rules for a good ontology:

  • Start small. 5–10 entity types max for v1. Add types only when you have queries that need them.
  • Canonical labels. Customer (not customer / Cust / Client). Document this list.
  • Inheritance lite. Use a generic label + specific label: (p:Person:Customer). Lets you query all People or all Customers.

3. Provenance & audit trails

Every fact in your KG should carry its origin: which document, which line, which extraction job, when, with what confidence. This is what auditors ask for — and what lets you fix wrong data without re-ingesting the world.

The pattern: every entity/edge has properties:

(o:Order {
  id: 9981,
  date: "2026-05-10",
  source_doc: "shopify_export_2026_05.csv",
  extracted_at: "2026-05-12T03:14:00Z",
  extraction_job_id: "j-281",
  confidence: 0.98
})

When something looks wrong, you can answer in 30 seconds: "where did this come from, by which job, with what confidence." Without it: archaeology.

4. Constraints & schema design

Neo4j enforces three classes of constraints. Set them on Day 1:

  • Uniqueness. No two Customers with the same email. CREATE CONSTRAINT FOR (c:Customer) REQUIRE c.email IS UNIQUE
  • Existence. Every Order must have a date. REQUIRE o.date IS NOT NULL
  • Type. Refund amount must be a float. REQUIRE r.amount IS :: FLOAT

Without constraints, LLM extraction quietly inserts duplicates, missing fields, and type errors. With them, bad data fails loudly at ingestion — which is what you want.

5. Structured reasoning via traversal

The killer feature: multi-hop queries. "Which customers ordered Product X in the last 30 days AND filed a damage report?"

MATCH (c:Customer)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product {name: "Widget A"}),
      (o)-[:HAS_REPORT]->(r:DamageReport)
WHERE o.date > date() - duration("P30D")
RETURN c.name, o.id, r.summary

This is the same query you'd write in SQL with 4 joins, but reads as a picture of relationships. KGs shine when you ask questions that cross entities — exactly the questions vectors can't answer.

Likely interview / investor / hiring questions

Q: When do you reach for a knowledge graph instead of (or alongside) a vector store?
A: When my data has relationships that matter to queries. "Find customers who bought X and filed a complaint" is a graph traversal — vectors can't represent the structural facts. I default to vector for "similar text" needs; add graph when queries cross entities. Often both: vectors for fuzzy recall, graph for structured constraints.
Q: How do you keep an LLM-built KG from drifting?
A: Three guardrails. (1) Strict ontology — a documented list of allowed entity types, relationship types, properties. (2) Schema constraints in Neo4j (uniqueness, existence, types). Bad extractions fail loudly. (3) Provenance on every fact — when something drifts, I can trace which job inserted it and re-run with a tightened extractor.
