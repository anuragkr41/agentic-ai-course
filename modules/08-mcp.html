MCP — Model Context Protocol

The open standard for connecting AI agents to tools. The "USB-C of AI" — write one server, every agent can use it.

⏱ ~65 min · 3 videos + 1 walkthrough · 10 MCQs + 3 scenarios · ≥80% to unlock M9

Why this matters

Before MCP, every agent framework invented its own tool format. Building a Slack integration meant separate code for Claude, GPT, Gemini, and every framework. MCP (introduced by Anthropic in late 2024, standardized through 2025-26) replaces that with one protocol. Write an MCP server once; every MCP-compatible agent can use it. As of 2026 it's the default interop layer for serious agentic systems.

1. MCP architecture

Three roles:

  • Host. The AI application (Claude Desktop, Cursor, your own agent).
  • Client. Inside the host — one client per connected MCP server.
  • Server. Exposes capabilities: tools (functions), resources (read-only data), prompts (templates).

What an MCP server exposes:

  • Tools. Functions the agent can call. Tool contracts (name, description, input schema, output schema) follow Module 2's rules.
  • Resources. Read-only data the agent can subscribe to or fetch (files, DB schemas, API docs).
  • Prompts. Templated prompts the host can use (e.g., a "summarize document" prompt the server author wrote).

2. Tool contracts in MCP

An MCP tool definition looks like (TypeScript SDK):

server.tool({
  name: "lookup_order",
  description: "Fetch order details by order ID. Use before any refund decision.",
  inputSchema: {
    type: "object",
    properties: {
      order_id: { type: "string", pattern: "^[0-9]+$" }
    },
    required: ["order_id"]
  }
}, async ({ order_id }) => {
  // implementation — runs in your secure backend
  return { date, amount, status };
});

Notice: same five fields as Module 2's tool contracts. MCP didn't invent the contract — it standardized how clients discover contracts and call them. That's the breakthrough.

3. Secure tool access

MCP servers are doors into your systems. Three rules:

  • Read-only by default. Every tool you ship starts as a read. Write tools are added explicitly, one by one, with explicit reason.
  • Allowlist scope. The Slack server doesn't expose all 200 channels — only the 3 the agent legitimately needs. Pinecone search? Only the indexes for this product. Postgres? Only the views, never the base tables.
  • Authentication per server. MCP supports OAuth, API keys, mTLS. Each server authenticates separately. Compromise one, the rest stay safe.

4. Auditable execution

Every MCP server should log:

  • Which client called. Identity (which host / which agent / which user, if forwarded).
  • Which tool, what input. Full input JSON.
  • What output. Full response.
  • When & how long. Timestamp, latency.
  • Whether HITL gated. Was a human approval involved? Who approved?

Pair this with Module 10's Langfuse traces and you have the chain: agent decision → MCP call → side effect → audit. End-to-end reconstructable.

5. Ecosystem & migration path

As of 2026:

  • Hosts that speak MCP: Claude (Anthropic), Cursor, Continue, Zed, Windsurf, plus most major agentic frameworks via plugins.
  • Pre-built MCP servers: filesystem, Postgres, GitHub, Slack, Gmail, Google Drive, AWS, GCP, Notion, Linear, Stripe, Figma. The list grows monthly.
  • SDKs: TypeScript, Python, Rust, Java, C#. Building a custom server is ~50 lines.

Migration: for each internal capability your agents use today, ask "should this become an MCP server?" Usually yes, because (a) other agents/teams will reuse it, (b) it forces clean security boundaries, (c) it future-proofs against framework changes.

Likely interview / investor / hiring questions

Q: Why bet on MCP?
A: Vendor independence and reuse. Before MCP, every framework had its own tool format — switching from LangChain to Microsoft Agent Framework meant re-implementing every integration. MCP standardizes the contract, so the same Postgres or Slack server works for any compliant agent. Anthropic championed it but it's open and adopted across the industry. It's the "USB-C for AI" — and on the same maturity curve.
Q: How do you keep an MCP server safe?
A: Read-only by default — every tool ships as a read; writes added one at a time with explicit reason. Allowlist scope — Slack server exposes 3 channels not 200; Postgres server exposes views not base tables. Per-server auth (OAuth, mTLS, API key) so compromise of one server doesn\'t cascade. Full audit log on every call. Pair with HITL gates from Module 1 on irreversible actions.
