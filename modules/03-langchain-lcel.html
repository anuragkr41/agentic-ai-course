1. The LangChain stack at a glance

LangChain isn't one thing — it's a toolkit of components plus a composition language (LCEL). The components are normalized wrappers around common building blocks: LLM clients, prompt templates, document loaders, splitters, embedders, vector stores, retrievers, output parsers, tools.

2. Document loaders & text splitting

Step one of any RAG system: get your documents into structured chunks the model can search. LangChain has loaders for ~200 formats (PDF, DOCX, HTML, S3, Notion, Google Drive, Confluence, etc.) — they all return the same Document type with text + metadata.

Then splitters chunk those documents. Wrong chunk size = bad retrieval; this is the #1 cause of underwhelming RAG. Three strategies:

  • Fixed-size (character or token). Simple, fast, loses semantic boundaries. Use 500–1500 token chunks with 10–20% overlap.
  • Recursive character. Tries paragraphs → sentences → words. Default for most prose. The LangChain default.
  • Semantic. Splits where meaning shifts (uses an embedder). Slower but best retrieval. Use for high-value corpora.

Founder rule: if your retrieval is bad, fix chunking first. Try 3 chunk sizes and measure recall before blaming the model.

3. Embeddings & vector stores

An embedding turns text into a numeric vector. Texts with similar meaning have similar vectors. A vector store indexes those vectors so you can search by similarity.

The decisions you actually make:

  • Embedder. OpenAI text-embedding-3-large (highest quality), Cohere, Voyage, or local models. Pick one and don't switch lightly — re-embedding your whole corpus is slow and expensive.
  • Vector store. Pinecone (managed), Chroma (local/dev), Weaviate, Qdrant (open-source), or use your existing DB — Postgres + pgvector works fine for ≤10M vectors and ships with most cloud DBs.
  • Hybrid search. Combine vector similarity with keyword (BM25) search. Materially better than vector alone — the "RAG is dead" video below explains why.

4. LCEL — composition language

LCEL (LangChain Expression Language) is how you wire components together. The big idea: every component is a Runnable; you pipe them with | (Python's bitwise-or operator, overloaded). 

chain = prompt | llm | output_parser
result = chain.invoke({"question": "What is our refund policy?"})

Read left-to-right: input flows into prompt, the rendered prompt goes to llm, the LLM's response goes to output_parser. Each pipe is a Runnable boundary.

What LCEL gives you for free:

  • Streaming. Tokens stream through the chain — you can show partial results in UI.
  • Batching. Run the same chain on 100 inputs in parallel with one call.
  • Async. Non-blocking, scales with your API server.
  • Retries. Built-in retry config per Runnable.
  • Tracing. Every Runnable boundary is a trace span — observability nearly free (Module 10).

5. Structured outputs (schema-first)

This is the single most important practice in this module. Force every LLM call to produce output matching a schema. Free-form text breaks production; schema-validated JSON survives. 

from pydantic import BaseModel

class RefundDecision(BaseModel):
    qualifies: bool
    amount: float
    reason: str
    confidence: float

chain = prompt | llm.with_structured_output(RefundDecision)
result: RefundDecision = chain.invoke({"case": case_data})
# result.qualifies, result.amount, etc. — typed, validated, no parsing

Why this matters for founders:

  • Downstream code stops breaking. If result.amount is always a float, your accounting service can rely on it.
  • Validation is the guardrail. Schema rejects malformed output before it touches a database or customer.
  • Evals get easier. Schema-typed outputs are auto-comparable; you can check exact correctness, not just "did the LLM say roughly the right thing."

6. Reliability: validation, retries, fallbacks

Three layers protect a production LCEL chain:

  1. Schema validation (above). Reject malformed outputs.
  2. Retries with backoff. If the LLM fails schema or returns an error, retry up to N times. chain.with_retry(stop_after_attempt=3).
  3. Fallbacks. If the primary LLM fails repeatedly, fall back to a cheaper/different model. primary.with_fallbacks([secondary]).

What this looks like end-to-end:

primary = ChatAnthropic(model="claude-opus-4-7").with_structured_output(RefundDecision)
secondary = ChatOpenAI(model="gpt-4o").with_structured_output(RefundDecision)

reliable_chain = (
    prompt
    | primary.with_fallbacks([secondary]).with_retry(stop_after_attempt=3)
)

Founder takeaway: insist your team adds these three layers to every customer-facing chain. Internal-only tools can skip the fallback if cost matters.

7. Deployment patterns

Three patterns. Pick by use case:

  • API service. Wrap your chain in a FastAPI / Express endpoint. LangServe auto-generates this for any chain. Use for real-time use cases.
  • Batch / scheduled. Run the chain over a list of inputs on a cron schedule. Use for nightly reports, bulk classification.
  • Embedded. Run the chain inside another app (e.g., a Slack bot, a CRM plugin). Use when you don't need a standalone service.

Likely interview / investor / hiring questions

Q: How would you make a LangChain pipeline production-reliable?
A: Three layers. (1) Schema-validated structured outputs — no free-form JSON. (2) Retries with backoff on transient failures. (3) Fallbacks to a secondary provider when the primary fails repeatedly. On top, instrument LCEL traces so I can see exactly which Runnable failed when something breaks.
Q: Our RAG retrieval is bad. Where do you look first?
A: Chunking, almost always. Try three chunk sizes (500, 1000, 1500 tokens) and measure retrieval recall on a labeled set. Second look: hybrid search — adding BM25 alongside vector usually adds 10–20 points. Third: reranker on top-50 results. Only after these is the embedder or model worth touching.
Q: When wouldn't you use LangChain?
A: When the task is a single LLM call with no retrieval, no tools, no chaining — LangChain is overhead. When the team has Go/Rust/Java only and Python isn't on the table — use that stack's native LLM SDK. When vendor lock-in is unacceptable and you'd rather code directly against OpenAI/Anthropic SDKs to keep dependencies minimal.
