1. What to evaluate

Six signals, in priority order:

  • Task success rate. Did the agent achieve the goal? Binary or graded; measured on a labeled set.
  • Schema validity. Did the output match the spec? Easy to automate; ship-blocker if <99%.
  • Groundedness. (Module 5.) For RAG, is every claim supported by retrieved evidence?
  • Citation coverage. % of claims that cite.
  • Cost per task. $ spent. Track p50 and p99.
  • Latency. Time-to-first-token, time-to-completion. Track p50 and p99.

Plus domain-specific signals: refund accuracy, classification F1, retrieval recall@k, etc. Start narrow — 4–6 signals total. More is paralysis.

2. Judge-model patterns

Many signals (groundedness, faithfulness, helpfulness) need a model to judge an output. The pattern: a separate LLM call grades the agent's output against criteria.

judge_prompt = """
Given the question, the retrieved context, and the answer, score:
- groundedness (0-1): every factual claim is supported by context
- citation_coverage (0-1): every claim cites a chunk
- helpfulness (0-1): the answer actually addresses the question

Return JSON: { groundedness, citation_coverage, helpfulness, reasoning }
"""

Three rules for honest LLM-as-judge:

  • Use a different (often stronger) model. Don't have GPT-4o grade GPT-4o; it's lenient on itself. Use Claude or Gemini as judge for GPT, or vice versa.
  • Calibrate against humans. Have humans label 50 examples. Run the judge. Measure agreement. If judge agrees <85% with humans, the prompt needs work.
  • Force reasoning. Judge must include its reasoning. Lets you spot when the judge is sloppy and improve the prompt.

3. Langfuse: traces, spans, runs

Three primitives:

  • Trace. One end-to-end user interaction. Has metadata (user_id, session, etc.).
  • Span. A unit of work inside a trace. Each LLM call, retrieval, tool call, sub-chain is a span. Spans nest.
  • Score. A measurement attached to a trace or span — could be an automatic eval result, a user thumbs-up, a manual review verdict.

4. Prompt & version tracking

Every prompt has a version. Every trace records which prompt version it used. When quality drops, you know exactly which prompt change to roll back.

Langfuse (and peers) provides a prompt registry: store prompts in the platform, reference by name + version in code, deploy a new version as a config change rather than a code release. This is huge for tight iteration loops.

5. Experiments & A/B testing prompts

The discipline: no prompt change ships without a regression check.

How:

  1. Build a dataset — 50–500 representative inputs with expected outputs.
  2. Run the current prompt over the dataset. Save scores.
  3. Run the candidate prompt over the same dataset.
  4. Compare per-input. Which got worse? Why? Reject if regressions outweigh gains.
  5. Promote the winning prompt to production. Old prompt remains in the registry (rollback in seconds).

6. Cost & latency monitoring

  • Cost per task. p50 (median) and p99 (tail). p99 is where the surprises hide — a few runaway agents can blow your budget.
  • Latency. Time to first token (UX-critical for chat) and time to completion.
  • Budgets and alerts. Hard cap per task. Alert on p99 spikes. Daily report by feature.
  • Cost attribution. Tag traces by feature, customer, environment. When the bill spikes you can pin down where.

Likely interview / investor / hiring questions

Q: How do you know your agent is getting better, not worse, over time?
A: Labeled eval dataset (200+ cases) run against every prompt/model change. Six signals tracked: task success, schema validity, groundedness, citation coverage, cost, latency. LLM-as-judge for subjective signals, calibrated against humans on 50 cases. Regression check is automated; failing changes don\'t ship. Quarterly: update the dataset with new failure modes captured in production. Without this, "is it better" is vibes.
Q: An LLM provider updates a model. What do you do?
A: Three things in sequence. (1) Run the eval dataset against the new model — pin down quality delta on every signal. (2) Run a shadow deploy: route 5% of production traffic to new model, compare scores live. (3) If both pass, gradual rollout: 25% → 50% → 100% with rollback if any score regresses. Without traces and eval, this is impossible — you\'d find out from customer complaints, which is the wrong feedback loop.
