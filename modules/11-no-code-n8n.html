Why this matters

Not every agentic workflow needs to be a Python pipeline. A founder who wants to automate "when a deal closes in HubSpot, draft a welcome email, post to Slack, and create a Notion page" can do that in n8n in an afternoon — no engineering ticket needed. The lesson isn't "n8n replaces engineering." It's most internal automations should start in a no-code tool. Promote to code only when complexity demands it.

2. Triggers & actions

An n8n workflow is a graph: nodes are actions (do something), edges are connections (data flowing from one to the next). The first node is a trigger — the thing that kicks the workflow off.

Trigger types you\'ll use:

  • Webhook. External service sends an HTTP request. Stripe payment, GitHub issue, anything with webhooks.
  • Schedule. Cron. "Every weekday 9am send the daily digest."
  • App event. Built-in connectors poll the service (new Gmail, new HubSpot deal, new Notion row).
  • Manual / form. You or a teammate clicks a button or fills a form.

3. Approvals in workflows

n8n supports HITL natively. Use the Wait node with a "resume on webhook" or "resume on email" mode. Workflow pauses, sends a Slack/email asking for approve/reject, resumes on response. Persists across days. Same pattern as Module 4\'s LangGraph interrupt — different UI, same idea.

Apply Module 1\'s rule: gate the irreversible (send_email, charge_card, write to prod DB), audit the reversible (read-only lookups, draft generation).

4. Integrations

n8n ships with 600+ connectors. The ones you\'ll actually use:

  • Communication: Slack, Teams, Discord, Email (SMTP, Gmail, Outlook), Twilio (SMS)
  • CRM & sales: HubSpot, Salesforce, Pipedrive
  • Productivity: Notion, Airtable, Google Sheets, Google Drive
  • Dev & data: GitHub, Linear, Postgres, MySQL, MongoDB, Webhook (anything HTTP)
  • AI: OpenAI, Anthropic, Hugging Face, vector stores (Pinecone, Qdrant, Weaviate)

For anything missing, the HTTP Request node lets you call any REST API. So "n8n doesn\'t support X" is rarely a blocker.

5. Audit logs & governance

Two governance moves for n8n at scale:

  • Execution log. Every workflow run is logged — inputs, outputs, errors, time. Retain for as long as compliance demands. Searchable.
  • Workflow review. Before a workflow goes to production, a designated owner reviews it: triggers, credentials, scope of actions, who approves. Same as code review but for visual workflows. Quarterly re-review of active workflows.

6. Security considerations

  • Credentials in one place. n8n\'s credential store. Never hardcode API keys in node fields.
  • Least-privilege credentials. The "Gmail send" workflow should use a Gmail account that can only send (not read inbox). Same logic as Module 9.
  • Allowlist recipients on send actions. Same rule as in code: an n8n workflow that sends email should target a curated list, not "any email."
  • Self-host for sensitive data. n8n is open-source. Cloud is fine for non-sensitive work; self-host when data can\'t leave your network.
  • Workflow change control. Production workflows shouldn\'t be edited live by anyone. Stage in dev → review → promote.

Likely interview / investor / hiring questions

Q: Why use n8n if you have engineers?
A: Two reasons. One: business-team workflows shouldn\'t require engineering tickets. "Notify Slack when a deal closes" is a 30-minute n8n workflow, not a 2-day engineering investment. Two: my engineers should be writing the code that matters — the agentic logic, the data pipelines, the customer-facing app. Internal glue is a poor use of expensive engineers. n8n moves that glue to people who can own it directly.
Q: How do you stop n8n becoming a security risk?
A: Three controls. (1) Centralized credentials — never hardcoded in workflows; least-privilege scopes per credential. (2) Workflow review before production — designated owner approves the workflow same way we\'d code-review a PR. (3) Audit log retained; quarterly review of active workflows. Self-host when data sensitivity requires it. Same governance as code; just visual.
