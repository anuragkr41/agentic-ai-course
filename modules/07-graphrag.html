1. Graph traversal & multi-hop reasoning

Vector RAG can answer "what's our refund policy?" by finding a chunk that says so. It cannot answer "which of my Tier-A customers bought from supplier X in Q1 AND had a recall AND are still active?" — because those facts are scattered across entities, and the LLM has to reason about connections, not just text.

Graph traversal walks the relationships. Two hops, three hops, N hops — until you reach the answer. The agent picks the path.

2. Hybrid retrieval — three lanes, one answer

The state of the art: run all three retrieval modes in parallel, then merge.

How to weight the lanes:

  • "What is …" questions → vector dominant. Look up definitions.
  • "Find docs containing exact term X" → full-text dominant. Product codes, names, IDs.
  • "Which entities relate to Y and Z by path?" → graph dominant. Compliance, fraud, recall scope.
  • Most real queries → all three, with the agent learning which signals matter from logs.

3. Evidence + path response pattern

The output schema that customers love and auditors accept:

class GraphRAGAnswer(BaseModel):
    text: str
    evidence: list[Citation]      # the chunks (from vector/full-text lanes)
    path: list[Edge]              # the graph traversal that connected entities
    confidence: float

The path field is the killer feature. Your answer shows "we connected Customer Anurag to Supplier SupplyCo via this 4-hop path: Anurag → Order #9981 → Widget A → Batch #B-12 → SupplyCo." A user can visually verify; a regulator can audit; a debugger can spot extraction errors.

4. When to use GraphRAG (and when not)

Use GraphRAG whenStick with vector RAG when
Data has explicit relationships (org charts, supply chains, financial ledgers)Data is flat documents with no structural cross-refs
Queries are multi-hop or constrained ("X who Y and Z")Queries are "find similar text"
You need to show the path for compliance / debugShowing citations is enough
Same entity appears across many documentsDocuments are independent

Likely interview / investor / hiring questions

Q: Pitch GraphRAG to a customer who already has vector RAG working.
A: "Vector RAG is great for 'what does our doc say about X' questions. GraphRAG is for 'which of our customers are exposed to the SupplyCo recall' — questions that need you to traverse relationships. We layer graph on top, not replace. Vector still answers most queries; graph answers the ones that lose deals when you can't answer them. And every answer comes with a traversal path users can verify — that's what regulators want to see."
Q: When wouldn't you bother with GraphRAG?
A: When my data is flat documents with no entity overlap (e.g., a research paper corpus where each paper is independent). When my queries are all "what does this document say." When I won't invest in ontology + extraction maintenance. The honest test: can I name three queries today that vector RAG fails on? If no, don't build GraphRAG yet.
