MCP Tool-Augmented Agent

An MCP server exposing safe, governed tools — usable by any compliant agent or framework. The pattern that ends "we re-implemented integrations for every framework."

Prerequisites: M2 · M8 · M9 · Build time: 3–5 engineering weeks

Problem statement

Across your product line, four agents (a customer support agent, an internal data agent, an SDR-assist agent, and a research copilot) all need to interact with the same underlying systems: Postgres for customer data, Slack for notifications, GitHub for issues, Stripe for refunds. Today, each agent re-implements those tool integrations in its own framework. Every new integration is N copies; every bug is duplicated N times; every security review is N reviews.

Why a founder builds this

  • Reuse. Write each integration once as an MCP server; all four agents pick it up.
  • Security review is single-source. Compliance reviews the MCP server once, not the integration in every agent.
  • Framework independence. When you swap an agent\'s framework next quarter (LangGraph → Microsoft Agent Framework, or whatever), integrations are untouched.
  • External distribution. An MCP server exposing your product\'s API becomes the way third-party agents (Claude Desktop, Cursor, anyone\'s custom agent) integrate with you. Distribution surface — not just internal tooling.

Architecture

Component breakdown

ComponentModule(s)What it does
Tool contractsM2, M8Each tool: name, one-sentence description, strict input schema, output schema, side-effect flag. Discovery via MCP\'s tools/list.
postgres-serverM8, M12SELECT-only via UC views; allowlist of view names; query parser rejects writes / non-allowlisted; LIMIT injected; dry-run cost cap.
slack-serverM8, M9post_message scoped to 3 channels via allowlist; bot scope (not user-account scope); audit per call.
github-serverM8search_issues (read), comment (write, HITL-gated). Scoped to 2 repos. GitHub App auth (revocable per server).
stripe-serverM8, M9refund tool only. Idempotency keys mandatory. Hard HITL gate at agent layer + dollar threshold inside server. Read-only Stripe creds for everything else.
AuthenticationM8, M9Per-server credentials; least privilege; rotated automatically; central secret manager.
Audit logM9, M10Every call: identity, tool, input, output, ts, latency, HITL outcome. Tagged for cost/latency tracking in Langfuse.
Capability discoveryM8Agents call tools/list on init; cache for the session. Server changes (new tool, new scope) ripple automatically.

Design decisions you can defend

  • MCP, not custom protocol. Open standard with multi-framework adoption (Anthropic, Microsoft, LangChain all support it). No vendor lock-in.
  • Read-only default; writes added one tool at a time. postgres-server has no write tool, period. stripe-server has one write tool, with multiple gates.
  • Allowlist scope per server. slack-server can only post to #support-internal, #cs-alerts, #refunds-approved. github-server only touches 2 repos. Views-only for postgres.
  • Per-server credentials. Compromise of slack-server credentials doesn\'t cascade. Each server\'s blast radius is its own scope.
  • HITL stays at the agent layer. MCP is transport. The agent decides when to gate. (Don\'t bury HITL inside a server — it makes the server reusable for non-HITL contexts.)
  • Idempotency keys on every write tool. Refund key = case_id. Same key → no double-charge if any agent retries.
  • Single audit log across all servers. Unified queryability for compliance.

Interview / investor / customer talking points

Q: Why MCP, not direct tool integration in each agent?
A: Reuse and vendor independence. Without MCP, the same Postgres or Slack integration is duplicated across N agents — every bug and every security review is duplicated too. With MCP, we write each integration once. When we swap an agent\'s framework (this happens at least once a year), integrations are unaffected. And it\'s an open standard — Anthropic, Microsoft, and LangChain all support it.
Q: How do you stop an attacker who hijacks one MCP server from cascading?
A: Per-server credentials. The slack-server\'s OAuth token only works for the 3 allowlisted channels; compromise gives the attacker nothing beyond that scope. The stripe-server is even more restricted. There is no global "MCP credential" — each server is independently authenticated, independently scoped, independently rotatable.
Q: What\'s the long-term play here beyond internal use?
A: Distribution. The same MCP servers we use internally can be exposed to customers — they connect their own agents (Claude, Cursor, custom) to our platform via the same protocol. We become a node in the broader MCP ecosystem instead of one more SaaS API documented in a PDF. Strategic moat: developers prefer the open protocol over custom integrations.
Q: Why isn\'t HITL inside the server?
A: Separation of concerns. The server\'s job is to expose a capability safely. HITL is a policy decision that depends on context (agent, user, query type) — that belongs at the agent layer. Burying HITL in the server makes the server unusable for legitimate non-HITL contexts (e.g., internal admin tooling).

Resume bullets for Project 3

Designed and deployed 4 production MCP servers (Postgres, Slack, GitHub, Stripe) exposing scoped, read-only-default tools to 4 different agent frameworks — replacing 16 duplicated integrations with 4 reusable services and unifying security review.
Architected per-server authentication, scoped allowlists, idempotency keys, and unified audit logging — ensuring compromise of a single MCP server has bounded blast radius and that every tool call across the agent fleet is reconstructable for compliance.
Future-proofed the agent stack against framework churn — when frameworks change (LangGraph → Microsoft Agent Framework etc.), the underlying MCP-exposed integrations remain unchanged, saving estimated 6 engineering weeks per framework migration.
