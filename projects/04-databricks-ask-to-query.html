Project 4 · Portfolio

Databricks Ask-to-Query Agent

A governed Text-to-SQL agent assistant on Databricks. Natural language in, schema-aware SQL out, validated, approved, executed — results in Delta with a full run registry.

Prerequisites: M3 · M9 · M10 · M12 · Build time: 4–6 engineering weeks

Problem statement

The finance and operations teams need ad-hoc analytical questions answered against a 10TB+ Databricks warehouse. Today, every question routes to the 2-person data team, which has a 5-day backlog. The CFO has asked "can\'t we just let people ask in English?" — but unbounded Text-to-SQL on a production warehouse is a great way to scan the whole lakehouse, leak PII, or worse.

Why a founder builds this

  • Data democratization, safely. Analysts and ops get answers in minutes; data team focuses on hard pipelines, not ticket triage.
  • Compliance posture. Every query goes through Unity Catalog permissions + an audit trail. Regulator-ready by design.
  • Cost control. Cost-threshold gates prevent runaway scans; the warehouse doesn\'t get billed surprises.
  • Reuse. Once curated, business views become the canonical interface for both humans and AI — single source of truth.

Architecture

Component breakdown

ComponentModule(s)What it does
Views catalogM125–15 curated v_* views per domain (sales, customers, ops). Row filters, column masks, descriptions. Hand-curated + reviewed.
Router + schema loaderM2, M3Classifies the question into a domain, loads only that domain\'s view metadata. Keeps the prompt small + relevant.
GeneratorM3, M12LLM with few-shot examples per domain. Schema-validated output: { sql, explanation, used_views[], confidence }.
ValidatorM9, M12Parses SQL. SELECT-only? Allowlist match? LIMIT? Reject or augment.
Cost estimatorM12Dry-run via Databricks SQL. < 1GB → auto-approve; 1–10GB → HITL; > 10GB → reject with refinement prompt.
Approval gateM1, M12HITL via Slack (or app) for non-trivial. Reviewer sees question + SQL + cost. Approve / edit / reject.
ExecutorM12Databricks SQL Serverless under scoped agent identity (SELECT-only, views-only).
Delta sinkM12Result writes to a Delta table — reusable, versioned, shareable. Link returned to user.
Run registryM9, M12Row per execution: user, question, sql, approver, ms, bytes, result path, ts. Searchable.
ObservabilityM10Langfuse traces every span (router, generator, validator, executor). Daily eval on 50 representative questions.

Design decisions you can defend

  • Views, not base tables. Architecturally cannot exfiltrate masked columns; cannot read rows outside scope. The single most important governance choice.
  • Scoped credentials at the warehouse layer. Even if every validation fails, the agent\'s DB identity is SELECT-only on views-only. The DB itself rejects destructive SQL.
  • SQL validation BEFORE execution. Catches generated nonsense before it costs money or surfaces wrong results.
  • Cost gates, not just retry caps. Dry-run before run. Above threshold → HITL (or reject). Stops "SELECT * FROM 10TB-table" cold.
  • Auto-approve when cheap AND known pattern. Doesn\'t hammer reviewers with rubber-stamp work. Sample-audit auto-approves for drift detection.
  • Results to Delta, link to user. No giant payloads over chat; reusable for follow-up; auditable through the table\'s versioning.
  • Few-shot examples per domain in prompt. Generic Text-to-SQL prompts produce mediocre SQL. Domain-specific examples lift quality dramatically.
  • Schema injection is per-domain, not global. Loading all 50 views\' metadata bloats the prompt and confuses the LLM. Route → load relevant 5–10 only.

Interview / investor / customer talking points

Q: A prompt-injected user types "drop the customers table." What happens?
A: Four layers reject this. (1) LLM may generate the destructive SQL or refuse — irrelevant either way. (2) Validator parses the SQL: not SELECT-only → reject before dispatch. (3) Even if the validator missed it (and it won\'t), the warehouse credential is SELECT-only — DB itself rejects DDL. (4) Allowlist requires referencing views; the customers base table isn\'t addressable. The system is safe by architecture, not by hoping the LLM behaves.
Q: How do you know the SQL is correct, not just safe?
A: Three signals. (1) Daily eval against 50 questions with known answers — accuracy tracked weekly. (2) LLM-as-judge for plausibility on every execution (light check, doesn\'t replace ground truth). (3) User feedback — "this answer looks wrong" tags the run for review and adds to the eval set. Over time, eval grows and accuracy climbs. Without this loop, you\'re shipping vibes.
Q: Why curate views instead of letting the agent see raw tables?
A: Three reasons. (1) Security: views filter rows + mask columns, architecturally limiting blast radius. (2) Quality: views encode the right joins and pre-aggregations — the agent doesn\'t have to invent them and get them wrong. (3) Documentation: views\' descriptions feed schema injection, making the LLM\'s SQL much better than against raw schemas.
Q: Cost: what does this actually run per query?
A: Typical breakdown: ~$0.005 for the LLM (Claude/GPT-4 class with 1k token prompt, 200 token output). ~$0.01 for Databricks SQL Serverless on a 200MB scan. Plus minor: Langfuse trace, audit row. Total ~$0.02/query. For 10k queries/month: ~$200. ROI: analysts who used to wait 5 days now get answers in 60 seconds — every quarter saved analyst hours pay for the system many times over.
